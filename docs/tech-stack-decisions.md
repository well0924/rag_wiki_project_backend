# 기술 스택 선택 이유

각 기술을 **왜 골랐는지, 무엇과 비교했는지, 대신 무엇을 감수했는지** 정리한 문서입니다.
기능 단위의 개별 결정(업로드 방식, 그룹 이름 규칙, 배포 SSH 등)은 [decision-log](decision-log.md)에 있습니다.

> 공통 전제: **EC2 t3.small(메모리 2GB) 1대, 1인 개발, 공개 데모.**
> 대부분의 선택은 "서버 한 대에 다 올라가는가"와 "혼자 운영할 수 있는가"를 먼저 따졌습니다.

---

## 한눈에 보기

| 영역 | 고른 것 | 비교한 것 | 핵심 이유 |
|---|---|---|---|
| 백엔드 언어 | Kotlin + Spring Boot 3 | Java + Spring | null 안전성, 코루틴으로 AI 서버 호출 대기 처리 |
| AI 서버 | Python FastAPI (분리) | Spring에서 직접 처리 | 임베딩·청킹 생태계가 Python에 있음, 무거운 작업을 API 서버와 분리 |
| 벡터 저장소 | PostgreSQL + pgvector | Pinecone, Qdrant 등 전용 DB | 권한 조건을 벡터 검색 쿼리 안에 넣을 수 있음, 컨테이너 하나 절약 |
| 비동기 큐 | Redis Streams | Kafka, RabbitMQ | 이미 쓰는 Redis 재사용, 2GB 서버에 브로커를 따로 못 올림 |
| 임베딩 / LLM | OpenAI text-embedding-3-small, gpt-4o-mini | 로컬 모델(distiluse) | 측정해 보니 로컬 모델은 관련·무관 질문 유사도가 겹침 |
| 인증 | JWT + Redis(블랙리스트·Refresh Token) + Google OAuth2 | 세션 | 프론트(Vercel)와 API 도메인이 다름, 로그아웃 즉시 무효화 |
| 정리 작업 | Spring Batch | `@Scheduled`만 사용 | 벡터 → 파일 → DB 순서 삭제를 단계로 나누고 실행 기록을 남김 |
| 배포 | Docker Compose + Caddy + Jib + GHCR + GitHub Actions | k8s, ECS, Nginx | 서버 한 대에 맞는 가장 단순한 구성, HTTPS 자동 |
| 비용 | EventBridge Scheduler로 02:00~08:00 중지 | 24시간 운영 | 데모라 새벽 사용이 없음 |
| 프론트 | Next.js + Vercel | EC2에 같이 배포 | 2GB 서버 메모리를 백엔드에 몰아줌 |

## 1. Kotlin + Spring Boot 3

**고른 이유**
- `?` 타입으로 null 가능 여부가 컴파일 단계에서 드러남. 권한 판정처럼 "값이 없을 때"가 버그로 이어지는 코드가 많음
- `suspend` 컨트롤러와 코루틴으로 AI 서버 응답(수 초)을 기다리는 동안 스레드를 붙잡지 않음 (`SearchController`, `SearchUsecase`)
- data class, 확장 함수로 DTO·변환 코드가 짧아짐

**비교한 것**: Java + Spring. 생태계는 같지만 null 처리와 비동기 대기 코드가 길어짐

**감수한 점**
- JPA 엔티티를 위해 `allOpen`, `kotlin-jpa` 플러그인 설정이 필요
- 코루틴(`suspend`) 안에서 JPA(블로킹)를 부를 때 스레드를 의식해야 함
- 비동기 요청 기본 제한(30초)이 WebClient 대기(60초)보다 먼저 끊겨 첫 질문이 500이 났던 문제를 겪음 → 70초로 조정 (포트폴리오 7번)

## 2. AI 서버를 Python FastAPI로 분리

**고른 이유**
- 청킹(토큰 단위), 임베딩, OpenAI SDK, pgvector 클라이언트가 Python 쪽이 가장 성숙함
- 임베딩·적재는 무겁고 오래 걸림. API 서버(Spring)와 프로세스를 나누면, 인덱싱이 몰려도 로그인·목록 같은 요청이 같이 느려지지 않음
- 역할 경계가 분명함: **Spring = 누가 무엇을 볼 수 있는지 결정**, **FastAPI = 받은 그룹 ID 범위 안에서 검색만**

**비교한 것**: Spring AI 등으로 Spring 안에서 직접 처리. 서버는 하나로 줄지만 무거운 작업이 API 서버와 섞임

**감수한 점**
- 서버 간 통신이 생겨 내부 API 키, 내부 경로 차단(Caddy), 타임아웃 조정이 필요
- 테스트도 Spring 116개 / Python 34개로 나뉘어 두 군데서 관리

## 3. PostgreSQL + pgvector (전용 벡터 DB 대신)

**고른 이유**
- **가장 중요한 이유: 권한 조건을 벡터 검색 쿼리 안에 넣을 수 있음.** 문서 공개 그룹 테이블과 같은 DB라 `EXISTS`로 권한을 확인한 뒤 유사도 순으로 정렬할 수 있음. 권한 밖 청크는 후보에도 오르지 않음 (포트폴리오 문제 1)
- 전용 벡터 DB를 쓰면 권한 정보를 메타데이터로 복제해야 하고, 그룹에서 빠졌을 때 두 저장소를 동시에 고쳐야 함
- 회원·문서 DB와 같은 컨테이너라 2GB 서버에 컨테이너 하나를 아낌

**비교한 것**: Pinecone(외부 유료 서비스), Qdrant·Chroma(컨테이너 추가)

**감수한 점**
- 대규모(수백만 청크)에서는 전용 DB보다 느릴 수 있음. 지금 규모에서는 문제 없음
- 벡터 테이블은 AI 서버가 소유하고, Spring은 직접 건드리지 않음 (삭제는 배치가 AI 서버 API로 요청)

## 4. Redis Streams (Kafka 대신)

**먼저: 왜 비동기여야 했나**
- 인덱싱(청크 나누기 → 청크마다 임베딩 API 호출 → pgvector 적재)은 문서가 길수록 오래 걸리고, 외부 API(OpenAI) 응답 속도에 따라 달라짐
- 업로드 요청 안에서 이걸 다 하면 사용자는 그동안 화면을 붙잡고 기다려야 하고, 요청이 타임아웃으로 끊기면 "올라간 건지 아닌지" 알 수 없음
- 그래서 업로드 요청은 **텍스트 추출 · 원본 저장 · 문서와 공개 그룹 저장 · 이벤트 발행까지만** 하고 바로 응답. 인덱싱은 AI 워커가 따로 하고, 화면에는 상태(`UPLOADED` → `PROCESSING` → `COMPLETED` / `FAILED`)로 보여 줌
**Redis Streams를 고른 이유**
- 서버가 t3.small 한 대(약 1.9GB)라 Kafka 브로커를 따로 올릴 여유가 없음
- 캐시·토큰 저장에 이미 Redis를 쓰고 있어 새 인프라 없이 비동기 파이프라인을 만듦
- 소비자 그룹, ACK, PEL(확인 안 된 메시지 목록)이 있어 "처리 후에만 ACK → 죽으면 다시 가져오기(At-least-once)"를 구현할 수 있음. 단순 Pub/Sub는 구독자가 없으면 메시지가 사라짐

**비교한 것**
| | Redis Streams | Kafka | RabbitMQ |
|---|---|---|---|
| 추가 인프라 | 없음 (기존 Redis) | 브로커 + 메모리 큼 | 브로커 추가 |
| 재처리 | PEL + XCLAIM | 오프셋으로 처음부터 다시 읽기 | 큐 재전달 |
| 보관 | 메모리, `MAXLEN ~1000` | 디스크, 장기 보관 | 소비하면 삭제 |

**감수한 점**
- 최근 약 1,000건만 보관해 오래된 이벤트를 처음부터 다시 읽을 수 없음 → 원본과 상태는 DB에 있어 재업로드·재발행으로 복구
- 본문 전체를 이벤트에 싣는데 Redis가 `maxmemory 100mb`, `noeviction`이라 큰 문서는 발행이 실패할 수 있음 → 업로드 5MB·200,000자 제한
- 지금은 `DocumentService`가 Redis에 직접 발행함. Kafka로 옮기려면 `FileStorage`처럼 발행 부분을 인터페이스로 먼저 분리해야 함

## 5. OpenAI 임베딩·LLM (로컬 모델 대신)

**고른 이유**
- 로컬 모델(distiluse, 512차원)로 재 보니 관련 질문 0.13~0.22, 무관 질문 0.06~0.14로 **범위가 겹쳐 기준값으로 거를 수 없었음**
- OpenAI `text-embedding-3-small`은 관련 최저 0.345, 무관 최고 0.199로 기준 0.3이 그 사이에 들어감
- 로컬 모델은 서버 메모리(AI 컨테이너 상한 300MB)와 첫 요청 로딩 시간 부담이 큼
- 답변은 `gpt-4o-mini`: 문서 내용만으로 답하고 `[1]` 출처를 붙이는 일이라 큰 모델이 필요 없고 비용이 낮음

**감수한 점**
- 호출마다 비용이 듦 → 근거가 없거나 소속 그룹이 없으면 OpenAI를 부르지 않음, 업로드 제한, 새벽 서버 중지
- 질문 횟수 제한은 아직 없음 (다음 할 일)
- 외부 API 장애 시 검색이 멈춤 → 일시적 오류는 재시도, 키 누락처럼 반복되는 오류는 바로 DLQ

## 6. 인증: JWT + Redis + Google OAuth2

**고른 이유**
- 프론트(Vercel)와 API(EC2) 도메인이 달라 세션 쿠키보다 토큰 방식이 단순함
- JWT만 쓰면 로그아웃해도 만료 전까지 유효함 → **Redis 블랙리스트**에 남은 만료 시간만큼 등록해 즉시 무효화
- Refresh Token은 Redis에 저장하고 쓸 때마다 교체. 탈취된 토큰이 먼저 쓰이면 불일치로 감지해 둘 다 막음
- 요청마다 회원·그룹을 DB에서 읽지 않도록 **인증 캐시**(`user-cache:v3:{email}`, 30분)
- Google 로그인 후 토큰을 URL에 바로 싣지 않고 **일회용 로그인 코드**를 넘긴 뒤 프론트가 교환 → 토큰이 브라우저 기록·리퍼러에 남지 않음

**감수한 점**
- 캐시가 남아 있는 동안 예전 권한이 쓰일 수 있음 → 권한 구조가 바뀔 때 캐시 키 버전을 올림 (v2 → v3)
- Access Token은 탈취되면 만료(30분)까지 유효. 짧은 수명으로 피해 시간을 제한

## 7. Spring Batch (삭제 문서 정리)

**고른 이유**
- 문서 삭제는 화면에서는 즉시(Soft Delete), 실제 정리는 새벽 3시에 **벡터 → 원본 파일 → DB 순서**로 함. 순서가 바뀌면 DB에는 없는데 벡터만 남아 검색에 걸릴 수 있음
- Reader(삭제 표시 문서 조회) → Processor(벡터 삭제 요청 + 원본 파일 삭제) → Writer(공개 그룹·문서 행 삭제)로 역할이 나뉘고, 100건씩 끊어 처리해 문서가 많아도 메모리를 일정하게 씀 (`DocumentSyncBatchConfig`)
- 실행 결과가 배치 메타데이터 테이블에 남아 언제 몇 건 처리됐는지 확인 가능
- 읽은 행을 바로 지우므로 일반 페이징을 쓰면 행을 건너뜀 → 항상 첫 페이지만 다시 읽도록 함

**비교한 것**: `@Scheduled` 메서드 하나로 처리. 단순하지만 대량 처리 시 트랜잭션·메모리 관리와 실행 기록을 직접 만들어야 함

**감수한 점**: 배치 메타데이터 테이블이 생기고 설정이 늘어남. 처리 중 멈춘 문서(30분 초과 → `FAILED`)처럼 단순한 작업은 `@Scheduled`로 둠

## 8. 배포: Docker Compose + Caddy + Jib + GHCR + GitHub Actions

**고른 이유**
- **Docker Compose**: 서버 한 대에 5개 컨테이너(Caddy, Spring, FastAPI, PostgreSQL, Redis). 컨테이너마다 메모리 상한을 두고 스왑 2GB로 버팀. k8s·ECS는 이 규모에 비해 운영 부담과 비용이 큼
- **Caddy**: 설정 몇 줄로 Let's Encrypt 인증서 자동 발급·갱신. 내부 전용 API(`/api/v1/internal/*`) 차단도 같이 처리. Nginx + certbot보다 설정과 갱신 관리가 적음
- **Jib**: Dockerfile 없이 Gradle로 이미지 빌드. 의존성 레이어가 나뉘어 코드만 바뀌면 빠르게 다시 올라감
- **GHCR**: GitHub Actions 토큰으로 바로 푸시, 비공개 저장소. 서버에는 읽기 권한 토큰만 둠
- **GitHub Actions (수동 실행)**: 배포하는 1~2분 동안만 러너 IP를 22번에 열고 끝나면 지움 ([decision-log 2026-11-15](decision-log.md))

**감수한 점**
- 서버 한 대라 장애 시 전체가 멈춤, DB 백업 아직 없음
- 배포마다 22번을 잠깐 열어야 함 → AWS SSM으로 바꿔 22번을 닫을 계획

## 9. 비용: EventBridge Scheduler

**고른 이유**: 데모라 새벽 사용자가 없음. 02:00 중지 / 08:00 시작(Asia/Seoul)으로 EC2 시간을 1/4 줄임. Lambda 없이 EC2 API를 바로 부를 수 있음

**감수한 점**: 새벽에는 접속 불가(배포 주소 옆에 운영 시간 표기). 역할에 권한 정책을 빠뜨려 이틀 동안 조용히 실패한 적이 있음 → CloudTrail로 찾아 고침 (포트폴리오 7번)

## 10. 프론트: Next.js + Vercel

**고른 이유**
- 2GB 서버 메모리를 백엔드 쪽에 몰아주려고 프론트는 EC2에서 뺌
- Vercel은 푸시하면 자동 배포되고 HTTPS가 기본
- 【본인 확인: Next.js(React)를 고른 이유. 예) 익숙함, App Router 경험 등】

**감수한 점**: 도메인이 달라 CORS와 OAuth 리다이렉트 주소를 프론트 주소 하나로 정확히 맞춰야 함
