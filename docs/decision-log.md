## 2026-11-19 검색: 표현에 따라 같은 뜻의 질문이 검색되지 않음 (개선 보류)

**발견**
- 데모 리허설에서 demo-b(플랫폼개발팀)로 질문했을 때:
  - "배포는 언제 해?" → 서비스 배포 절차 문서를 찾아 "매주 목요일 오후 2시"로 답함
  - "정기 배포는 언제 해?" → 관련 문서를 찾지 못함
- 문서에는 "정기 배포는 매주 목요일 오후 2시에 진행합니다"라는 문장이 그대로 있다.
- 추가 확인(같은 날): "배포는 어떻게 돼?", "배포의 주기는 어떻게 돼?"는 답이 나왔다. 실패한 표현은 지금까지 "정기 배포는 언제 해?" 하나다.
  - 문서에 있는 단어("정기")를 그대로 넣은 질문이 오히려 실패해서, 단어 일치와 검색 결과가 비례하지 않는다.

**원인 (추정)**
- 검색은 단어 일치가 아니라 벡터 유사도(코사인)로 한다.
- 임베딩은 로컬 모델(distiluse, 512차원)이며 한국어의 표현 차이에 민감하다.
- 유사도 하한 `SEARCH_MIN_SIMILARITY = 0.3`(Python 서버 `app/config.py`)보다 낮은 청크는 버린다. "정기 배포" 질문은 이 기준을 넘지 못한 것으로 보인다.
- 질문별 실제 유사도 점수는 아직 확인하지 않았다.

**선택지**
| | 내용 | 특징 |
|---|---|---|
| A. 평가셋으로 기준값 검증 | 질문 20~30개와 정답 문서를 정하고 0.25 / 0.3 / 0.35에서 정답률 비교 | 원래 "검증 예정"이던 작업. 근거 있는 기준값을 얻음 |
| B. 하이브리드 검색 | 벡터 검색에 키워드 검색(PostgreSQL 전문 검색 등)을 섞음 | 문서에 단어가 그대로 있는 경우를 잡아 줌. 구현량 있음 |
| C. 임베딩 모델 교체 | `EMBEDDING_PROVIDER=openai` (text-embedding-3-small) | 설정으로 전환 가능하게 이미 만들어 둠. 비용 발생, 전체 재인덱싱 필요 |
| D. 청크 크기 조정 | 500토큰 → 200토큰, 또는 제목(##) 단위로 자르기 | 짧은 문서는 지금 통째로 한 청크라 한 문장의 의미가 묻힐 수 있음. 재인덱싱 필요 |

**결정**
- 지금: 코드는 바꾸지 않는다. 데모 녹화에는 검색되는 표현("배포는 언제 해?")을 쓴다.
- 시연 후: A(평가셋)부터 해서 문제의 크기를 숫자로 확인하고, 그 결과로 B나 C를 정한다. 질문별 유사도 점수를 로그로 남기는 것도 함께 검토한다.

**이유**
- 기준값과 모델을 근거 없이 바꾸면 다른 질문이 깨질 수 있다. 측정부터 한다.

## 2026-11-18 그룹 이름 중복 규칙: 만든 사람(OWNER) 기준으로 변경 (2026-11-19 적용)

**배경**
- 그룹 이름은 서비스 전체에서 하나만 쓸 수 있다 (`GroupService.createGroup`의 중복 검사, `user_group.group_name` UNIQUE).
- 데모 계정(demo-a)으로 "인사팀", "개발팀"을 만들려 했더니, 다른 계정이 예전에 만든 같은 이름 때문에 `DUPLICATE_GROUP_NAME`으로 막혔다.
- 로그인한 회원 누구나 그룹을 만들 수 있어서 회사 팀뿐 아니라 스터디 같은 모임도 만들 수 있다. 서로 모르는 사람이 같은 이름("스프링 스터디")을 못 쓰는 건 이 쓰임새와 맞지 않는다.

**선택지**
| | 내용 | 특징 |
|---|---|---|
| A. 중복 허용 | ID로 구분, 화면에 이름과 OWNER, 설명 표시 | 가장 자유롭지만 멤버 추가 시 헷갈릴 수 있음 |
| B. 만든 사람 기준으로 하나 | `(OWNER, 그룹 이름)` 조합만 겹치지 않게 | 내 실수는 막고, 남과는 겹쳐도 됨 |
| C. 지금처럼 전체에서 하나 | 그대로 | 사내 위키 하나만 쓴다는 가정일 때만 자연스러움 |

**결정**
- 지금: C를 유지하고, 데모 그룹 이름을 **경영지원팀**(인사 문서), **플랫폼개발팀**(개발 문서)으로 바꿔 시연 영상을 먼저 찍는다.
- 시연 후: 규칙을 수정한다. B가 유력하며, 수정할 때 이 항목을 갱신한다.

**이유**
- 규칙을 바꾸면 DB 제약까지 바뀌어 테스트와 배포를 다시 해야 한다. 시연 일정을 먼저 지킨다.

**적용 (2026-11-19, 시연 영상 완료 후): B**
- `GroupService`: 생성·수정 시 "요청한 회원이 OWNER인 그룹 중 같은 이름"이 있는지만 검사한다. 수정할 때는 그 그룹 자신을 제외한다.
- `UserGroupMemberRepository.countGroupsByMemberRoleAndName`: OWNER 정보가 매핑 테이블(`user_group_members.role`)에 있어서, DB 복합 유니크 제약 대신 조회로 검사한다.
- `UserGroup.groupName`: 전체 유니크 제약(`unique = true`)을 제거했다. `UserGroupRepository.findByGroupName`도 제거했다.
- 오류 문구: "이미 같은 이름의 그룹을 만들었습니다. 다른 이름을 입력해 주세요."

**감수한 점**
- DB 제약이 없어서, 같은 회원이 생성 버튼을 거의 동시에 두 번 누르면 같은 이름이 2개 생길 수 있다. 본인 그룹 안의 일이라 영향이 작아 감수한다.
- 멤버 추가 화면 등에서 남이 만든 같은 이름의 그룹이 보일 수 있다. 사용자는 자기가 속한 그룹만 보므로 지금은 문제없다. 헷갈리는 경우가 생기면 OWNER 이름을 함께 표시한다.

**운영 DB 반영 (수동)**
- `ddl-auto=update`는 기존 유니크 제약을 지우지 않는다. 배포 후 운영 DB에서 직접 삭제해야 한다.
  ```sql
  -- 1. 제약 이름 확인
  SELECT conname FROM pg_constraint WHERE conrelid = 'user_groups'::regclass AND contype = 'u';
  -- 2. 확인한 이름으로 삭제
  ALTER TABLE user_groups DROP CONSTRAINT <제약이름>;
  ```
- 삭제하지 않으면 코드는 바뀌어도 다른 사람과 같은 이름을 만들 때 DB에서 막혀 500 오류가 난다.

## 2026-11-15 배포: 배포하는 동안만 러너 IP를 SSH에 임시 허용

**배경**
- 보안 그룹 22번(SSH)은 관리자 집 IP 하나(`/32`)만 허용한다.
- GitHub Actions 러너는 실행마다 IP가 달라서 SCP 단계에서 `dial tcp ...:22: i/o timeout`으로 실패했다. 이미지 빌드와 GHCR 푸시는 성공했다.
- EC2에는 탄력적 IP가 붙어 있어 주소는 고정이다. 막힌 원인은 주소가 아니라 보안 그룹이다.

**선택지**
| | 내용 | 평가 |
|---|---|---|
| A. 수동 반영 | Actions는 빌드까지, 반영은 직접 SSH | 집 밖에서는 반영 불가 |
| B. 러너 IP 임시 허용 | 배포 직전 러너 IP를 22번에 추가, 끝나면 삭제 | 주소와 SSH 방식 유지, AWS 키 필요 |
| C. Tailscale | EC2와 PC, 러너를 사설망으로 묶음 | 카페 접속까지 해결되지만 가입·설치 필요 |
| D. SSM | SSH 대신 Systems Manager로 명령 | 22번 폐쇄 가능, IAM 역할과 워크플로 재작성 필요 |
| E. 22번 전체 개방 | `0.0.0.0/0` | 제외 |

**결정: B**
- 지금 주소, 키, SCP/SSH 단계를 그대로 두고 단계 2개만 추가하면 된다.
- 22번이 열리는 시간은 이미지 빌드가 끝난 뒤 배포하는 1~2분이다.
- 삭제 단계는 `if: always()`로 실패해도 실행하고, `concurrency`로 배포가 동시에 돌지 않게 했다.

**감수한 점**
- AWS 키를 GitHub Secrets에 둔다. IAM 권한은 이 보안 그룹의 인바운드 규칙 추가·삭제만 허용한다.
- 카페 등 집 밖에서 MobaXterm 접속은 여전히 안 된다. 필요하면 브라우저 접속(EC2 Instance Connect)이나 C(Tailscale)를 검토한다.
- 러너가 삭제 단계 전에 강제 종료되면 임시 규칙이 남을 수 있다. 설명이 `github-actions-deploy`인 규칙이 보이면 수동으로 지운다.

## 2026-11-14 문서 업로드: 요청 1건 = 파일 1개

**배경**
- 백엔드는 한 요청에 여러 파일(`List<MultipartFile>`)을 받았지만 제목은 요청당 하나라, 여러 파일에 같은 제목이 붙었다.
- 프론트는 파일 1개만 보내고 있어서 다중 업로드 코드가 화면에서는 쓰이지 않았다.
- 검증은 전부 먼저 했지만, 저장 단계에서 3번째 파일이 실패하면 앞의 2개는 남는 부분 저장 문제가 있었다.

**선택지**
| | A. 파일마다 따로 요청 | B. 한 요청에 여러 파일 + 파일별 제목 목록 |
|---|---|---|
| 실패 처리 | 그 파일만 실패, 그 파일만 재시도 | 검증 실패 시 전부 거절 |
| 남는 문제 | 거의 없음 | 저장 단계 부분 저장 문제가 그대로 남음 |
| 코드 | 백엔드 단순화 | `titles[]` 매칭, 원자성 보강 필요 |

**결정: A**
- 위키 문서는 서로 독립이라, 5개 중 1개가 깨졌다고 나머지 4개를 막을 이유가 없다.
- 백엔드는 단일 `MultipartFile`만 받아 개수 제한이 저절로 생기고, 부분 저장 문제도 사라진다.
- 프론트는 여러 파일을 골라 파일별 제목을 정하고, 순서대로 하나씩 요청하며 파일별 상태(대기/업로드 중/완료/실패)를 보여 준다.

**감수한 점**
- 파일 5개면 요청도 5번이다. 데모 규모에서는 문제 없다.
- "한 번에 최대 5개"는 화면 제한이다. 서버는 요청 단위로만 막는다(요청당 1개).

**함께 정한 제한**
| 항목 | 값 | 위치 |
|---|---|---|
| 형식 | TXT, MD, PDF, DOCX | `DocumentService.ALLOWED_DOC_TYPES`, 화면 `ALLOWED_EXTENSIONS` |
| 파일 크기 | 5MB (기본값 1MB에서 상향) | `spring.servlet.multipart.max-file-size`, 화면 `MAX_FILE_SIZE_MB` |
| 요청 크기 | 25MB | `spring.servlet.multipart.max-request-size` |
| 추출 글자 수 | 200,000자 | `DocumentService.MAX_CONTENT_LENGTH`, 화면 `MAX_TEXT_LENGTH` |
| 한 번에 고르는 개수 | 5개 | 화면 `MAX_FILE_COUNT` |

- 글자 수 상한 이유: 본문 전체가 Redis Streams 이벤트에 실리고, Redis는 `maxmemory 100mb` + `noeviction`, 스트림은 최근 1,000건을 유지한다. 5MB TXT가 그대로 실리면 발행이 실패할 수 있다.
- 값을 바꿀 때는 백엔드와 화면을 함께 바꾼다.

**참고: 일반적인 업로드 방식과 비교**
- 파일·문서 서비스(구글 드라이브, 노션, 슬랙)는 여러 개를 고르고 파일마다 따로 요청하는 방식이 일반적이다. 이번 결정도 같다.
- 한 요청에 여러 파일은 게시글 + 첨부처럼 묶음이 한 단위일 때 맞다. 위키 문서는 각자 독립이라 해당하지 않는다.

**나중에 검토할 것**
- 2~3개씩 동시 전송: 지금은 순서대로 하나씩 보낸다. 5개 규모에서는 체감 차이가 작아 보류했다.
- S3 Presigned URL 직접 업로드: S3 도입 시 함께 검토한다. `FileStorage` 인터페이스로 저장소를 분리해 둔 상태다.
