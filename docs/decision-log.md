## 2026-11-14 문서 업로드: 요청 1건 = 파일 1개

**배경**
- 백엔드는 한 요청에 여러 파일(`List<MultipartFile>`)을 받았지만 제목은 요청당 하나라, 여러 파일에 같은 제목이 붙었다.
- 프론트는 파일 1개만 보내고 있어서 다중 업로드 코드가 화면에서는 쓰이지 않았다.
- 검증은 전부 먼저 했지만, 저장 단계에서 3번째 파일이 실패하면 앞의 2개는 남는 부분 저장 문제가 있었다.

**선택지**
| | A. 파일마다 따로 요청 | B. 한 요청에 여러 파일 + 파일별 제목 목록 |
|---|---|---|
| 실패 처리 | 그 파일만 실패, 그 파일만 재시도 | 검증 실패 시 전부 거절 |
| 남는 문제 | 거의 없음 | 저장 단계 부분 저장 문제가 그대로 남음 |
| 코드 | 백엔드 단순화 | `titles[]` 매칭, 원자성 보강 필요 |

**결정: A**
- 위키 문서는 서로 독립이라, 5개 중 1개가 깨졌다고 나머지 4개를 막을 이유가 없다.
- 백엔드는 단일 `MultipartFile`만 받아 개수 제한이 저절로 생기고, 부분 저장 문제도 사라진다.
- 프론트는 여러 파일을 골라 파일별 제목을 정하고, 순서대로 하나씩 요청하며 파일별 상태(대기/업로드 중/완료/실패)를 보여 준다.

**감수한 점**
- 파일 5개면 요청도 5번이다. 데모 규모에서는 문제 없다.
- "한 번에 최대 5개"는 화면 제한이다. 서버는 요청 단위로만 막는다(요청당 1개).

**함께 정한 제한**
| 항목 | 값 | 위치 |
|---|---|---|
| 형식 | TXT, MD, PDF, DOCX | `DocumentService.ALLOWED_DOC_TYPES`, 화면 `ALLOWED_EXTENSIONS` |
| 파일 크기 | 5MB (기본값 1MB에서 상향) | `spring.servlet.multipart.max-file-size`, 화면 `MAX_FILE_SIZE_MB` |
| 요청 크기 | 25MB | `spring.servlet.multipart.max-request-size` |
| 추출 글자 수 | 200,000자 | `DocumentService.MAX_CONTENT_LENGTH`, 화면 `MAX_TEXT_LENGTH` |
| 한 번에 고르는 개수 | 5개 | 화면 `MAX_FILE_COUNT` |

- 글자 수 상한 이유: 본문 전체가 Redis Streams 이벤트에 실리고, Redis는 `maxmemory 100mb` + `noeviction`, 스트림은 최근 1,000건을 유지한다. 5MB TXT가 그대로 실리면 발행이 실패할 수 있다.
- 값을 바꿀 때는 백엔드와 화면을 함께 바꾼다.

**참고: 일반적인 업로드 방식과 비교**
- 파일·문서 서비스(구글 드라이브, 노션, 슬랙)는 여러 개를 고르고 파일마다 따로 요청하는 방식이 일반적이다. 이번 결정도 같다.
- 한 요청에 여러 파일은 게시글 + 첨부처럼 묶음이 한 단위일 때 맞다. 위키 문서는 각자 독립이라 해당하지 않는다.

**나중에 검토할 것**
- 2~3개씩 동시 전송: 지금은 순서대로 하나씩 보낸다. 5개 규모에서는 체감 차이가 작아 보류했다.
- S3 Presigned URL 직접 업로드: S3 도입 시 함께 검토한다. `FileStorage` 인터페이스로 저장소를 분리해 둔 상태다.
